# warpgen — локальный генератор WARP-конфигов для Amnezia

> **Ядро** — на базе `github.com/vernette/warpscout` (MIT).

Локальный CLI-инструмент на Go, который регистрирует WARP-аккаунт, сканирует
рабочие endpoint Cloudflare, проверяет DNS через туннель и выдаёт готовый `.conf`
для AmneziaWG с обфускацией. Туннель — userspace: без root, без TUN, без
`VpnService`, без изменения маршрутов системы.

## Требования

- Go ≥ 1.26.3
- Linux/macOS/Windows (разработка и тесты — на Linux)
- Сеть: доступ к API Cloudflare и к диапазонам WARP

## Сборка

```bash
make build          # статический бинарник ./warpgen (CGO_ENABLED=0)
make build-debug    # без -s -w
```

Статический бинарник собирается командой:

```bash
CGO_ENABLED=0 go build -tags netgo -ldflags "-s -w -extldflags '-static'" -o warpgen ./cmd/warpgen
```

## Запуск

```bash
# 1. Зарегистрировать аккаунт WARP (сохраняется в warpgen-account.json)
./warpgen register

# 2. Просканировать endpoint'ы и получить ранжированный список
./warpgen scan --max 512 --target 3

# 3. Проверить DNS через туннель на выбранном endpoint
./warpgen dns-check --endpoint 162.159.192.1:2408

# 4. Сгенерировать конфиг для AmneziaWG
./warpgen gen --endpoint 162.159.192.1:2408 --dns 1.1.1.1 --output warp.conf
```

Все команды принимают `--account` (файл аккаунта), `--fresh` (перерегистрироваться),
`--interface` (привязать UDP-сокет к интерфейсу, linux/root), `--json`, `--debug`.

### Что означают поля вывода `scan`

| Поле | Значение |
|---|---|
| `ENDPOINT` | `ip:port` рабочей точки входа Cloudflare |
| `SEEN AS` | регион, который видит внешний сервис через туннель (`loc` из `cdn-cgi/trace`) |
| `NODE` | узел Cloudflare, на который попал туннель (`colo`) |
| `RTT` | задержка, измеренная **внутри** туннеля (не ICMP) |
| `LOSS` | доля потерь внутри туннеля |
| `STATUS` | `OK` / `нет хендшейка` / `нет данных через туннель` / `регион RU` / `исключённый colo` |

Подходящими считаются endpoint'ы со стабильным (не срезанным ТСПУ) туннелем и без
colo DME/LED/KJA; они сортируются по возрастанию задержки. Регион `RU` больше не
отвергается: из России WARP всегда его отдаёт, поэтому такие endpoint'ы учитываются,
а строка ниже предупреждает об этом. Жёсткий режим — флаг `--strict-region`.

## Chain: AWG → WARP → Psiphon

Один WARP из России не меняет выходной регион (`loc=RU`), но если поверх внешнего
AWG-туннеля запустить **warp-plus** в режиме `--cfon`, он поднимает свой WARP, а
поверх него — Psiphon, и страну меняет именно Psiphon. Команда `chain` автоматизирует
это: проверяет внешний туннель, готовит identity для warp-plus, перебирает страны и
держит SOCKS5, пока процесс жив.

```bash
# 1. Внешний туннель: сгенерировать .conf и подключить его в AmneziaVPN
./warpgen gen --endpoint 162.159.192.1:2408 --output warp.conf

# 2. Запустить цепочку (страна NL, SOCKS5 на 127.0.0.1:8086)
./warpgen chain --countries NL,SE,DE,US,PL

# 3. Пользоваться прокси, пока процесс жив
curl --proxy socks5h://127.0.0.1:8086 https://ifconfig.co/json
```

warp-plus в проект не вшит — вызывается как внешний релизный бинарник v1.2.6
(`--warp-plus PATH`, иначе ищется в `PATH` и рядом с `warpgen`). Identity для него
собирается из аккаунта warpgen в `--cache-dir` (по умолчанию `warpgen-chain/`,
файл `primary/wgcf-identity.json`, права 0600); каталог в `.gitignore`, потому что
содержит приватный ключ.

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--warp-plus` | поиск в `PATH` и рядом | путь к бинарнику warp-plus |
| `--countries` | `NL,SE,DE,US,PL` | страны через запятую, порядок = приоритет (FI вручную, но он не работает) |
| `--endpoint` | `162.159.192.1:2408` | WARP-endpoint внутреннего туннеля |
| `--bind` | `127.0.0.1:8086` | адрес SOCKS5-прокси |
| `--cache-dir` | `warpgen-chain` | каталог identity warp-plus и кэша Psiphon |
| `--test-url` | `http://example.com/` | URL проверки связи внутри warp-plus (нужен `HEAD=200`, см. ограничения) |
| `--ready-timeout` | `100s` | сколько ждать готовности одной попытки |
| `--attempts` | `2` | попыток на страну |
| `--strict` | `true` | требовать совпадения страны (`--strict=false` — только «не RU») |
| `--account` | `warpgen-account.json` | файл аккаунта warpgen (источник identity) |

Критерий успеха попытки: `cloudflare.com/cdn-cgi/trace` по системному маршруту даёт
`warp=on` и узел не из DME/LED/KJA, а через SOCKS5 `ifconfig.co` и `ipinfo.io`
отвечают валидным JSON с корректным IPv4, при этом ни один не увидел `RU` (и при
`--strict` хотя бы один назвал запрошенную страну). Сбой всех стран — таблица попыток
с причиной (нет хендшейка WARP, гейт warp-plus, Psiphon не построил туннель, не та
страна) и ненулевой код возврата.

### Ручной рецепт тех же шагов

```bash
# 1. Скан → endpoint с NODE не DME/LED/KJA, затем .conf
./warpgen scan --max 512 --target 3
./warpgen gen --endpoint <ip:port> --output warp.conf

# 2. Импортировать .conf в AmneziaVPN и подключить, проверить внешний путь:
curl -s https://www.cloudflare.com/cdn-cgi/trace     # нужно warp=on, colo не DME/LED/KJA

# 3. Запустить warp-plus вручную (релизный бинарник v1.2.6):
warp-plus -4 -e 162.159.192.1:2408 -b 127.0.0.1:8086 --cfon --country NL \
  --test-url http://example.com/ --cache-dir warpgen-chain -v

# 4. Проверить выход через прокси:
curl --proxy socks5h://127.0.0.1:8086 https://ifconfig.co/json
curl --proxy socks5h://127.0.0.1:8086 https://ipinfo.io/json
```

### Известные ограничения chain

- **FI не работает** — Psiphon-этап там стабильно падает (`tunnel establishment timeout`),
  поэтому в список по умолчанию он не входит (хотя запросить можно вручную).
- **Страна не гарантирована:** Psiphon-этап проходит не всегда, а геосервисы могут
  расходиться (был случай: один и тот же IP — PL у `ipinfo.io` и FR у `ifconfig.co`);
  при расхождении печатаются оба ответа.
- **Скорость** через Psiphon — 0.3–0.8 МБ/с (контроль без Psiphon — до 3.45 МБ/с).
- **Нужен внешний туннель** (AmneziaVPN и т.п.) без выхода через российские узлы;
  без него команда завершается с подсказкой.
- **Грабля warp-plus v1.2.6:** своя проверка связи — это HTTP `HEAD` к `--test-url`
  с требованием ровно `200`, а Cloudflare сейчас отдаёт на `HEAD /cdn-cgi/trace` 404.
  Поэтому по умолчанию берётся обходной `--test-url http://example.com/`.
- **Бинарник — только релизный v1.2.6:** сборка из исходников на Go ≥ 1.24 падает
  (`panic: tls.ConnectionState doesn't match`), в CI проекта собирают под Go 1.22.

## Run: туннель, WARP и Psiphon в одном процессе

`chain` требует уже поднятого внешнего туннеля (AmneziaVPN и т.п.). Команда `run`
самодостаточна: сама поднимает внешний AWG-туннель **внутри процесса** (userspace,
без root и TUN, конфиг на диск не пишется), пускает через него UDP внутреннего WARP
локальным форвардером, запускает warp-plus с Psiphon и отдаёт SOCKS5 с выходом вне РФ.
С `--warp-only` Psiphon не запускается вообще: наружу отдаётся SOCKS5 прямо поверх
WARP-туннеля с обфускацией AWG (см. ниже).

```bash
./warpgen run --countries NL,SE,DE,US,PL
# ... события ...
# 12:04:31 готово: socks5://127.0.0.1:8086, страна NL, IP 203.0.113.9 (AS1234 ...), подготовка 42s
curl --proxy socks5h://127.0.0.1:8086 https://ifconfig.co/json
```

### Схема

```
клиент → SOCKS5 (warp-plus + Psiphon) → внутренний WARP
            ↑
      warp-plus -e 127.0.0.1:<порт форвардера>
            ↑
   UDP-форвардер (loopback) → userspace-туннель (AWG) → endpoint Cloudflare
```

1. **Preflight** — только локальные проверки: аккаунт warpgen, identity для
   warp-plus, бинарник warp-plus. Сетевых запросов нет.
2. **Выбор endpoint** — тот же скан, что у команды `scan`: предфильтр хендшейком,
   trace изнутри туннеля, отсев DME/LED/KJA, сортировка по задержке; берётся до
   `--endpoints` кандидатов.
3. **Внешний туннель** — userspace-туннель в памяти процесса и проверка трафика:
   `warp=on` и узел не из исключённых.
4. **Форвардер** — UDP-сессия на каждый локальный источник через туннель на
   `--warp-endpoint`; простой сессии 120 с, лимит сессий, пакеты длиннее MTU
   считаются как `oversize` и передаются как есть.
5. **Цепочка** — warp-plus с `-e <адрес форвардера>` и логика `chain` без изменений:
   готовность SOCKS5, страна по двум геосервисам, повторы, перебор стран.
6. **Мониторинг** — раз в 60 с: выход RU или 3 сбоя подряд меняют страну, мёртвый
   внешний туннель — пересоздание туннеля и форвардера на следующем endpoint. После
   первого `ready` процесс не сдаётся и повторяет цикл до SIGINT/SIGTERM.
7. **Остановка** — по Ctrl+C: дочерние процессы (вся группа), форвардер и туннель
   закрываются, в системе ничего не остаётся.

### Флаги `run`

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--countries` | `NL,SE,DE,US,PL` | страны через запятую, порядок = приоритет |
| `--endpoints` | `3` | сколько кандидатов внешних endpoint'ов использовать |
| `--bind` | `127.0.0.1:8086` | адрес SOCKS5-прокси |
| `--listen` | `127.0.0.1:0` | адрес UDP-форвардера (loopback, 0 — свободный порт) |
| `--warp-endpoint` | `162.159.192.1:2408` | внутренний WARP, куда форвардер отправляет пакеты |
| `--warp-plus` | поиск в `PATH` и рядом | путь к бинарнику warp-plus |
| `--cache-dir` | `warpgen-chain` | каталог identity warp-plus и кэша Psiphon |
| `--test-url` | `http://example.com/` | URL проверки связи внутри warp-plus (нужен `HEAD=200`) |
| `--ready-timeout` | `100s` | сколько ждать готовности одной попытки |
| `--attempts` | `2` | попыток на страну |
| `--strict` | `true` | требовать совпадения страны (`--strict=false` — только «не RU») |
| `--max` | `512` | сколько кандидатов проверять за скан |
| `--strict-region` | `false` | жёсткий скан: отвергать endpoint'ы с регионом RU |
| `--account` | `warpgen-account.json` | файл аккаунта warpgen |
| `--warp-only` | `false` | без Psiphon: SOCKS5 поверх самого WARP-туннеля (warp-plus, identity и страны не нужны) |
| `--tun` | `false` | системный туннель: весь трафик машины идёт по цепочке (нужен root) |
| `--tun-name` | `warpgen0` | имя TUN-интерфейса |
| `--tun-mtu` | `1400` | MTU TUN-интерфейса |
| `--dns` | `1.1.1.1:53,8.8.8.8:53` | резолверы для DNS через цепочку (`ip[:port]` через запятую) |
| `--udp` | `drop` | политика UDP: `drop` — отбрасывать (QUIC ломается, приложения уходят на TCP) |
| `--dry-run` | `false` | с `--tun`: показать системные команды (в stderr) и ничего не менять |
| `--json` | `false` | события строками JSON (по одному объекту в строке) |
| `--debug` | `false` | служебный вывод (в stderr) |

События пайплайна: `endpoint_selected`, `outer_up`, `outer_checked`, `forwarder_up`,
`socks_up`, `psiphon_starting`, `ready`, `tun_up`, `routes_applied`, `routes_reverted`,
`dns_selected`, `dns_failed`, `degraded`, `failover`, `stopped`. Секретов (ключей,
токенов) в них нет; в JSON-режиме подсказки уходят в stderr, чтобы поток stdout
оставался чистым NDJSON.

### Режим без Psiphon: `run --warp-only`

Psiphon не запускается вообще: наружу отдаётся SOCKS5 прямо поверх внешнего
WARP-туннеля с обфускацией AWG. warp-plus, его identity, `--cache-dir`, `--countries`
и внутренний WARP не нужны — только аккаунт warpgen. SOCKS5-сервер поднимает сам
`warpgen` (в процессе), поэтому отдельного бинарника рядом не требуется.

```
клиент → SOCKS5 (в процессе) → userspace-туннель (AWG) → endpoint Cloudflare
```

```bash
./warpgen run --warp-only                     # SOCKS5 на 127.0.0.1:8086
curl --proxy socks5h://127.0.0.1:8086 https://www.cloudflare.com/cdn-cgi/trace
# ... warp=on ... loc=RU
sudo ./warpgen run --warp-only --tun          # тем же туннелем — весь трафик машины
```

- **Выход остаётся российским:** Cloudflare назначает выходной IP по геолокации
  клиента, поэтому `loc=RU` — норма, а не сбой. Мониторинг проверяет только связь;
  после трёх сбоев подряд пересоздаёт туннель на следующем endpoint'е, страну не
  меняет.
- Быстрее полной цепочки: один туннель без внутреннего WARP и Psiphon (на замерах
  ~0.9 МБ/с против 0.3–0.8 МБ/с с Psiphon).
- С `--tun` работает так же: весь трафик машины идёт через этот единственный
  туннель. Событие `socks_up` сообщает адрес локального SOCKS5.
- SOCKS5 слушает только loopback (прокси отдаёт туннель без аутентификации) и
  занимает один порт на весь прогон: при failover меняется только туннель, а мост
  системного туннеля продолжает ходить на тот же адрес.

### Известные ограничения run

- **warp-plus — только релизный бинарник v1.2.6** (см. ограничения `chain`): сборка
  из исходников на Go ≥ 1.24 падает, клиент в проект не вшит.
- **FI не работает** — Psiphon-этап там стабильно падает.
- **Страна не гарантирована**, а геосервисы могут расходиться.
- **Скорость** — 0.3–0.8 МБ/с (двойной туннель плюс Psiphon).
- **Аккаунт нужен заранее:** `warpgen register` или готовый `--account`.
- Root не нужен. Внешний туннель поднимается внутри процесса, поэтому системный
  маршрут не меняется и посторонний VPN не требуется (но и не мешает).

### Системный туннель: `run --tun`

`--tun` заводит **весь трафик машины** в ту же цепочку:

```
приложение → TUN (198.18.0.1/15) → мост (gVisor netstack, promiscuous + spoofing)
                                     ├─ TCP → SOCKS5 CONNECT → Psiphon → WARP → AWG → Cloudflare
                                     ├─ UDP/TCP 53 → DNS-over-TCP через SOCKS5 → выбранный резолвер
                                     └─ остальной UDP, ICMP, IPv6 → отбрасываются (со счётчиками)
```

```bash
sudo ./warpgen run --tun                        # весь трафик машины через цепочку
sudo ./warpgen run --tun --dns 1.1.1.1:53,8.8.8.8:53
sudo ./warpgen run --tun --dry-run              # только напечатать системные команды
curl https://ifconfig.co/json                   # уже без --proxy: трафик идёт через туннель
```

**Нужен root:** создаётся TUN-интерфейс (`/dev/net/tun`) и меняются маршруты. Без
прав команда сразу выходит с подсказкой и ничего не делает; `--dry-run` работает без
root и **не** создаёт TUN и не трогает маршруты — он только читает текущий маршрут по
умолчанию (чтобы напечатать реальные команды) и печатает их.

Порядок запуска: цепочка готова (`ready`) → TUN и мост → маршруты → выбор DNS.
Остановка — в обратном порядке: маршруты и DNS, затем TUN и мост, затем цепочка.
Ошибка на любом шаге откатывает уже применённое. Ctrl+C снимает всё сам.
После `kill -9` (или сбоя питания) помогает `sudo warpgen tun-revert`: он
откатывает команды из файла состояния `~/.warpgen/state/<имя TUN>.st`, который
пишется атомарно после каждой системной команды, — см. чек-лист ниже. Ручные
команды остаются запасным вариантом, если файл состояния недоступен.

Что применяется (и снимается при выходе):

1. `ip link` — адрес и MTU TUN из `198.18.0.0/15`;
2. маршрут `/32` внешнего endpoint через физический шлюз: иначе UDP-сокет внешнего
   туннеля ушёл бы в наш же TUN и цепочка зациклилась; при смене endpoint маршрут
   обновляется;
3. маршрут по умолчанию через TUN двумя половинами — `0.0.0.0/1` и `128.0.0.0/1`:
   они перекрывают существующий default, не удаляя его;
4. `blackhole` для IPv6: мост работает только с IPv4;
5. системный DNS через `resolvectl` — на **соседний адрес подсети TUN**
   (`198.18.0.2`), а не на адрес интерфейса: пакет к собственному адресу ядро
   доставляет локально (таблица `local`), и запрос к мосту не попадает. При откате
   возвращаются **прежние серверы интерфейса**, а не `resolvectl revert`: revert
   стирает и то, что выставил NetworkManager, и интерфейс остаётся без DNS до
   переподключения. Если `resolvectl` нет, команда **не правит** `/etc/resolv.conf`
   молча, а предупреждает об утечке DNS (событие `dns_failed`) и продолжает работу.

DNS: перехватываются UDP и TCP на 53-й порт к любому адресу, запрос уходит выбранному
резолверу как DNS-over-TCP через SOCKS5 (кэша нет). Кандидаты (`--dns`) проверяются
через цепочку после `ready`, берётся самый быстрый; при смене звена выбор повторяется.
Всё остальное UDP идёт `--udp=drop`: QUIC (`UDP/443`) отбрасывается молча, чтобы
приложения откатывались на TCP.

**Чего не будет:** видеозвонков и игр на UDP (проброс UDP не реализован, точка
расширения — `handleUDP` в `vpn/bridge.go`), любого трафика по IPv6, ICMP-пинга, а
также сервисов, которым нужен QUIC и которые не умеют откатываться на TCP.

При failover цепочки TUN и маршруты **не снимаются**: новые соединения на секунды
падают, но трафик не уходит напрямую — это и есть kill switch.

|---|---|---|---|
| Linux (сделано) | `vpn/tun_linux.go`: `tun.CreateTUN`, `tun.CreateTUNFromFile` | `vpn/routes_linux.go`: команды `ip` и `resolvectl` | root, проверка до старта |
| Android | `vpn.DeviceFromFile` (fd отдаёт `VpnService.Builder`) → `vpn.Options.Device` | не нужен: адрес, маршруты и DNS задаёт сам VpnService; `RouteManager` — заглушка со статусом | проверки нет: `vpn.Options.CheckPrivileges` подменяется на пустую |
| Windows | Wintun (`vpn/tun_windows.go`) | `vpn/routes_windows.go`: `netsh interface ipv4 add route` / `CreateIpForwardEntry`; исключение endpoint — маршрутом `/32` | администратор |
| macOS | utun (`vpn/tun_darwin.go`) | `vpn/routes_darwin.go`: `route add` и `networksetup -setdnsservers` | root |

Общий контракт один: `vpn.Device` (чтение/запись IP-пакетов, имя, MTU, Close),
`vpn.RouteManager` (`Apply`/`SetEndpoint`/`Revert`) и `vpn.DialFunc` — мост, политика
пакетов и выбор DNS от платформы не зависят. Для Android в `vpn.Options` уже есть
`Device` (готовое устройство из fd) и `Protect(fd)` — на Linux он не нужен (петля
исключена маршрутом `/32`), а на Android подменяется на `VpnService.protect`.
Пока реализован только Linux: остальные ОС возвращают `vpn.ErrUnsupported` с
понятным сообщением.

### Чек-лист e2e (позже, на свободной машине)

Автоматизированные сетевые проверки помечены тегом `e2e` и в обычном прогоне не
запускаются:

```bash
WARPGEN_E2E=1 go test -tags e2e ./core/ -run E2E -v
```

| № | Проверка | Ожидание |
|---|---|---|
| 1 | warp-plus принимает `-e 127.0.0.1:<порт>` и проходит хендшейк через форвардер | цепочка доходит до `ready` |
| 2 | поведение netstack при пакетах больше MTU внешнего туннеля | процесс жив, в счётчике `oversize`, вывод — в логе (`TestE2EForwarderMTU`) |
| 3 | полный прогон `warpgen run` для NL и SE | страна подтверждена двумя геосервисами (`TestE2ERunReady` с `WARPGEN_E2E_COUNTRY`) |
| 4 | failover: искусственно оборвать внешний туннель | событие `failover` и пересоздание туннеля с форвардером на следующем endpoint |
| 5 | чистая остановка по Ctrl+C | нет дочерних процессов (`pgrep -a warp-plus`) и слушающих портов (`ss -lunp \| grep 8086`) |
| 6 | `sudo warpgen run --tun --dry-run` | печатает план и команды, в системе ничего не меняется (нет `warpgen0`) |
| 7 | `sudo warpgen run --tun`, затем `ip addr show warpgen0`, `ip route show`, `ip -6 route show blackhole`, `resolvectl status` | TUN поднят (`198.18.0.1/15`, MTU 1400), в системе есть `/32` endpoint мимо TUN, `0.0.0.0/1` и `128.0.0.0/1` через TUN, blackhole `::/0`, системный DNS — на соседний адрес подсети TUN (`198.18.0.2`); событие `routes_applied` |
| 8 | нет утечек DNS: `sudo tcpdump -ni <физический интерфейс> port 53` | запросов по 53-му порту мимо TUN нет |
| 9 | обычный сайт и `curl` по IP | `curl https://ifconfig.co/json` и `curl http://1.1.1.1/` отвечают, `curl -6` не проходит, `warpgen` переживает это |
| 10 | поведение при failover | события `failover` и `dns_selected`, маршруты и TUN остаются на месте, трафик не уходит напрямую |
| 11 | чистый откат после Ctrl+C | `ip route show` без `0.0.0.0/1`, `128.0.0.0/1` и `/32` endpoint, `ip -6 route` без blackhole, `ip link show warpgen0` — нет интерфейса, DNS возвращён (прежние серверы интерфейса), файл состояния удалён |
| 12 | восстановление после `kill -9` | `sudo ./warpgen tun-revert` печатает и выполняет отмену записанных команд (журнал `~/.warpgen/state/warpgen0.st` очищается, повтор сообщает «откат уже сделан»); запасной вариант — вручную: `sudo ip route del 0.0.0.0/1 dev warpgen0`, `sudo ip route del 128.0.0.0/1 dev warpgen0`, `sudo ip -6 route del blackhole default`, `sudo resolvectl revert <физический интерфейс>` |
| 13 | `sudo ./warpgen run --warp-only --tun`, затем `curl http://1.1.1.1/`, `ip route show`, `pgrep -a warp-plus` | трафик идёт через единственный туннель (выход RU, `warp=on`), маршруты и TUN снимаются после Ctrl+C, процесс warp-plus не запускается |

Пункты 6–12 требуют root и меняют сеть машины, поэтому автоматических тестов для них
в репозитории нет осознанно: прогон такого теста в обычном `go test ./...` (или в CI)
ломает сеть. Офлайн проверены мост, политика пакетов, DNS и откат команд
(`vpn/bridge_test.go`, `vpn/routes_linux_test.go`), а автомат пайплайна — на фейках
(`core/pipeline_test.go`).

## Структура пакетов

- `registration/` — неофициальный API Cloudflare, регистрация WARP, локальное хранение аккаунта
- `tunnel/` — userspace WireGuard/AmneziaWG-туннель, хендшейк, `cdn-cgi/trace`, замер задержки, платформенный bind
- `scanner/` — кандидаты (диапазоны × порты), предфильтр по хендшейку, фильтр colo DME/LED/KJA, учёт региона, ранжирование
- `dnscheck/` — проверка DNS через туннель (пресеты + произвольный IP)
- `config/` — генератор `.conf` (WARP-safe AWG 2.0) и генераторы I1 (QUIC/DNS/SIP/STUN)
- `chain/` — цепочка «внешний AWG-туннель → WARP → Psiphon»: запуск внешнего warp-plus и проверка SOCKS5
- `core/` — самодостаточный пайплайн `run`: автомат состояний (endpoint → туннель → форвардер → страны → мониторинг; либо SOCKS5 поверх туннеля в `--warp-only`), UDP-форвардер, локальный SOCKS5-сервер, события
- `vpn/` — системный туннель `--tun`: TUN-устройство, мост TUN→SOCKS5 на gVisor netstack, DNS через цепочку, маршруты и их откат (Linux)
- `cli/` — CLI-интерфейс (`register`, `scan`, `dns-check`, `gen`, `chain`, `run`)

## WARP-safe инварианты конфига

Зафиксированы в `config` и проверяются тестами:

- `S1 S2 S3 S4 = 0`, `H1 H2 H3 H4 = 1 2 3 4` — иначе Cloudflare не поймёт пакеты;
- `MTU = 1280`, `PersistentKeepalive = 25` (в секции `[Peer]`);
- обфускация: junk-пакеты `Jc/Jmin/Jmax` + `I1` (маскировка под QUIC), поле строго заглавное;
- порядок полей `[Interface]`/`[Peer]` — как в эталонных конфигах.

## Ограничения

- **Выходной регион RU (важно):** из России WARP всегда показывает внешним сервисам
  регион `RU` — Cloudflare назначает выходной IP по геолокации клиента, а не по узлу
  (замер: `loc=RU` у 77 из 77 рабочих endpoint'ов, `ipinfo.io`/`ifconfig.co` также
  видят Россию). Поэтому такие endpoint'ы теперь **учитываются** (вариант «пока
  приемлемо»), а в выводе появляется предупреждение. Цель «сервис не видит российский
  IP» один WARP из РФ **не решает** — для этого нужна цепочка через не-RU узел.
  Туннель при этом работает: ~77% endpoint'ов поднимают хендшейк, узлы FRA/HEL,
  задержка 70–200 мс.
- **VPN на устройстве:** если активен другой VPN, скан пойдёт через него — проверять при выключенном VPN.
- **ICMP:** не полагаемся на ICMP-пинг — задержку измеряем внутри туннеля.
- **Регистрация:** API `api.cloudflareclient.com` из РФ часто недоступен напрямую —
  тогда регистрация идёт через туннель, но для этого нужен уже существующий аккаунт (`--account`).
- **Перебор:** полный диапазон (`188.114.96.0/22` и др.) — это тысячи пар IP×порт;
  за прогон проверяется `--max` кандидатов, скан останавливается после `--target` находок.
  Автоподбор endpoint для `dns-check` (без `--endpoint`) ограничен 40–200 проверками.
