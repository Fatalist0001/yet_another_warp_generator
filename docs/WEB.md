# Веб-генератор конфигов (`web/`)

Сайт, который выдаёт `.conf` для AmneziaWG к WARP. Аккаунт WARP регистрирует
**сервер** (вариант B: ключи и адреса приходят с бэкенда), а сам конфиг
собирается **в браузере** — там же работают обфускация `I1`, junk-пакеты и
проверка WARP-safe инвариантов.

```
браузер                    сервер                      Cloudflare
────────                   ──────                      ──────────
POST /api/warp     →  POST /reg {key: наш pub}   →  аккаунт WARP
                   ←  PATCH /reg/{id} warp_enabled
                   ←  {privKey, peer_pub, client_ipv4, client_ipv6}
GET /api/dns       →  resolve4 + UDP-запрос к резолверу
                   ←  [{id, label, ips, ok, rttMs}]
собрать .conf (I1, junk, инварианты) → скачать
```

Почему так: браузер не может ни зарегистрировать WARP-аккаунт (нужен
`User-Agent`/`CF-Client-Version`, CORS не пустит), ни проверить endpoint
(WARP — UDP, а `fetch` — TCP), ни резолвить DNS-хостнеймы без DoH. Всё, что
требует сети, делает сервер; всё, что касается формата конфига, — браузер.

## Файлы

| Файл | Что делает |

| `test-server.js` | офлайн-тесты бэкенда: регистрация (фейковый fetch), UDP-проверка на loopback, HTTP-контракт |

Тесты: `make web-test` — JS-наборы (`cd web && node test.js && node test-dom.js
&& node test-css.js && node test-server.js`) плюс офлайн-тесты боевого
`webserver/`. Сеть не нужна: `fetch` подменён, UDP ходит на loopback,
регистрация/резолвер/проба DNS в Go-тестах — фейки.

`test-css.js` появился не зря: DOM-стаб не читает CSS, поэтому «класс в разметке
есть, а правила нет» и «`var(--x)` не объявлена» проходили незамеченными и
проявлялись только в браузере (так было с `.hidden`, `.bg-dot` и с анимациями,
которые ссылались на необъявленный `--ease-in-out`). Любая правка разметки или
стилей должна оставлять этот тест зелёным.

## Локальный запуск

```bash
make web-serve          # http://127.0.0.1:8080
PORT=9000 make web-serve
make web-kill           # остановить сервер, поднятый через web-serve
```

`web-serve` не занимает терминал: сервер уходит в фон, лог — `web/server.log`
(в git не попадает). Если порт занят прошлым запуском (EADDRINUSE), сначала
`make web-kill` — `pkill` ищет только `node dev-server.js`, другие процессы не
задевает.

Открыть страницу и нажать «Сгенерировать» — всё остальное произойдёт само:
`dev-server.js` зарегистрирует аккаунт в Cloudflare и вернёт ключи, страница
проверит DNS-пресеты (резолв + живость), подставит случайный endpoint и
соберёт `.conf`. Готовый конфиг открывается в нижней панели: копирование и
скачивание.

Главный экран — приборная панель: шапка, заголовок, одна кнопка на всю ширину
и живая таблица параметров (endpoint, DNS, MTU, профиль I1), которая обновляется
при каждой правке настроек. Настройки (endpoint и порт, профиль I1, junk,
MTU/keepalive, DNS, формат вывода) живут в выезжающей панели слева
(шестерёнка в правом верхнем углу), группы пронумерованы `01`…`06`.

Ручного ввода ключей нет: приватный ключ в интерфейсе не показывается.
Базовый адрес API — тот же origin, откуда открыта страница. Если страница
лежит на другом хосте, чем API, адрес задаётся параметром
`?api=http://127.0.0.1:8080` (в настройках поля нет — URL виден в адресной
строке и не «теряется» в `localStorage`). CSP боевого сервера разрешает
`connect-src` только свой origin, DoH и `--allowed-origins`; если страница
ходит к отдельному API, добавьте его origin в allowlist страницы (или отдайте
страницу с хоста, чья CSP это разрешает).

`dev-server.js` — **эталон для проверки**, а не продакшен: в нём CORS `*`, нет
TLS и постоянного хранилища. Он оставлен для быстрой локальной итерации над
интерфейсом. Публичный хостинг запускается командой `warpgen web`: тот же
контракт, но логика регистрации и DNS берётся из Go-пакетов `registration`,
`config` и `dnscheck`, а не дублируется в JS.

## Боевой запуск

```bash
make build
./warpgen web --listen 127.0.0.1:8080
```

Для публичного домена есть два варианта.

**За reverse proxy (рекомендуется).** Прокси терминирует TLS, а `warpgen web`
слушает loopback:

```bash
./warpgen web --listen 127.0.0.1:8080 --trust-proxy --hsts
```

Минимальный Caddyfile (Caddy сам получает сертификат и выставляет
`X-Forwarded-*`):

```caddyfile
warp.example.org {
    reverse_proxy 127.0.0.1:8080
}
```

Nginx должен передавать `Host`, `X-Forwarded-Proto`, `X-Forwarded-For` и
`X-Forwarded-Host`; без `--trust-proxy` сервер эти заголовки игнорирует.

`--trust-proxy` означает «верить `CF-Connecting-IP` / `X-Forwarded-For`,
`X-Forwarded-Proto` и `X-Forwarded-Host`». Включать его можно только тогда, когда перед сервером
стоит **свой** прокси, который сам выставляет эти заголовки: иначе клиент
подделает IP и обойдёт лимиты. Если страница и API на разных origin'ах,
добавьте origin страницы в allowlist:

```bash
./warpgen web --listen 127.0.0.1:8080 --trust-proxy --hsts \
  --allowed-origins https://warp.example.org
```

**Напрямую с TLS.** Сертификат и ключ — PEM:

```bash
./warpgen web --listen :443 \
  --tls-cert /etc/letsencrypt/live/example.org/fullchain.pem \
  --tls-key  /etc/letsencrypt/live/example.org/privkey.pem
```

Что уже сделано для публичного запуска:

- `/api/warp` — только `POST` с `Content-Type: application/json`; чужой
  `Origin` получает `403`, поэтому браузерная CSRF-форма не создаст аккаунт.
  `GET` возвращает `405`, а не меняет состояние.
- CORS по умолчанию только same-origin; `--allowed-origins` задаёт точный
  список. Заголовок `Access-Control-Allow-Origin` не бывает `*`.
- Лимиты: 10 регистраций/мин на IP, 60/час на IP, 60/мин всего, 30 проверок
  DNS/мин на IP (`--register-limit`, `--register-hour-limit`,
  `--register-global-limit`, `--dns-limit`). Плюс `--max-inflight` ограничивает
  одновременные регистрации, чтобы всплеск не открывал сотни запросов к
  Cloudflare.
- Отчёт DNS кэшируется на 60 секунд (`--dns-cache`), поэтому обновление
  страницы не запускает UDP-проверки заново.
- Security-заголовки: CSP (без внешних скриптов, шрифты только локальные),
  `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options: DENY`,
  `Permissions-Policy`, HSTS при TLS/`--hsts`.
- Таймауты HTTP-сервера, лимит тела запроса (1 КиБ), graceful shutdown по
  SIGINT/SIGTERM, журнал без query/тел/ключей.
- Аккаунты не хранятся: приватный ключ живёт только в ответе на запрос.
  В журнал уходят метод, путь, статус и длительность — без ключей.

Серверу нужны исходящие HTTPS к `api.cloudflareclient.com` (регистрация) и
UDP/53 к резолверам (проверка DNS). Если UDP/53 закрыт, `/api/dns` вернёт
пресеты с `ok:false` — это сеть хостинга, а не ошибка кода.

Ограничения, которые остаются у любого одиночного процесса:

- лимиты и кэш DNS — в памяти, сбрасываются при перезапуске и не общие для
  нескольких инстансов; для кластера нужен общий WAF/Redis или один инстанс;
- мотивированный абузер с большим пулом IP всё равно упрётся только в
  глобальный лимит. Для большого публичного сайта поставьте перед сервисом
  Cloudflare/WAF и квоты на `/api/warp`;
- TLS-сертификаты не обновляются автоматически: используйте reverse proxy
  (Caddy/nginx) или внешний ACME-клиент.

## Контракт API

### `POST /api/warp`

Регистрирует новый WARP-аккаунт и возвращает ключи (как в
[warp-generation](https://warp-generation.github.io)). Тело запроса — `{}`,
заголовок `Content-Type: application/json`. Регистрация меняет состояние на
стороне Cloudflare, поэтому метод небезопасный: так браузер не отправит запрос
с чужого сайта без CORS-разрешения.

```json
{
  "privKey": "yAnz5TF+lXXJte14tji3zlMNq+hd2rYUIgJBgB3fBmk=",
  "peer_pub": "bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=",
  "client_ipv4": "172.16.0.2",
  "client_ipv6": "2606:4700:110:8a36:df92:102a:9602:fa18"
}
```

`privKey` генерирует сервер (X25519), Cloudflare его не возвращает — его нужно
отдать клиенту один раз. Тело `{}` сервер не читает: ключ создаёт он сам.

Ошибки — всегда JSON с `code`:

| Код | HTTP | Значение |
|---|---|---|
| `RATE_LIMITED` | 429 | слишком много регистраций (локальный лимит или `HTTP 429: error code: 1015` от Cloudflare) |
| `UPSTREAM_TIMEOUT` | 504 | Cloudflare не ответил вовремя (таймаут клиента 15 с) |
| `UPSTREAM_UNAVAILABLE` | 503 | Cloudflare недоступен с сервера (нет сети/блокировка) |
| `REGISTRATION_FAILED` | 502 | Cloudflare ответил ошибкой на `/reg` |
| `SERVER_BUSY` | 503 | исчерпан `--max-inflight`; повторите через несколько секунд |
| `ORIGIN_NOT_ALLOWED` | 403 | `Origin` не совпал с собственным или allowlist |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | нет `Content-Type: application/json` |
| `REQUEST_TOO_LARGE` | 413 | тело запроса больше 1 КиБ |
| `BAD_REQUEST` | 400 | тело не удалось прочитать |
| `METHOD_NOT_ALLOWED` | 405 | не POST; в `Allow` — разрешённый метод |
| `NOT_FOUND` | 404 | нет такого файла или пути |

### `GET /api/dns`

Резолвит пресеты и проверяет живость **самих резолверов** (обычный UDP-запрос
`cloudflare.com A` напрямую в резолвер, не через туннель) с замером RTT:

```json
{"presets": [
  {"id":"comss","label":"Comss","host":"dns.comss.one",
   "ips":["1.2.3.4","6.6.6.6"],"liveIps":["1.2.3.4"],
   "ok":true,"rttMs":21,"note":""},
  {"id":"malw","label":"Malw","host":"dns.malw.link","ips":[],"liveIps":[],
   "ok":false,"rttMs":null,"note":"не резолвится"}
]}
```

- `ips` — все разрешённые адреса: сначала ответившие, затем мёртвые (для показа);
- `liveIps` — только те, что ответили на пробу. Именно они попадают в
  `DNS =` (все живые, обычно 1–3), поэтому мёртвый резолвер не тормозит первый запрос;
- `ok` у группы (`recommended` = Comss + Malw + GeoHide) означает «есть хотя бы
  один живой адрес», мёртвые хосты перечисляются в `note`;
- у одного имени бывает несколько A-записей, поэтому сервер проверяет до 4
  адресов параллельно и берёт лучший RTT.

В конфиг попадают только IP — WireGuard не принимает имена. Мёртвые пресеты в
списке остаются, но помечены и отключены в интерфейсе. «Свой DNS» — клиентская
опция: сервер её не присылает, поэтому страница добавляет её в список сама
(иначе она исчезала после первой проверки).

Отчёт кэшируется на 60 секунд: повторные открытия страницы не дёргают
резолверы. В `warpgen web` лимит — 30 проверок DNS в минуту на IP; кэш-hit
лимит не расходует.

Дополнительно: `GET /api/health` → `{"ok":true,"service":"warpgen-web",...}`,
`OPTIONS /api/*` → 204 с CORS-заголовками для разрешённого origin.
`warpgen web` отвечает `404` на незнакомые пути (никакого directory listing и
выхода за каталог), а `dev-server.js` при битом percent-encoding возвращает
`400 BAD_REQUEST` и не роняет процесс.

## Что собирается в браузере

Порядок полей совпадает с `config.Generate`:

```
[Interface]  PrivateKey, Address, DNS, MTU, S1..S4, Jc/Jmin/Jmax, H1..H4, I1
[Peer]       PublicKey, AllowedIPs, Endpoint, PersistentKeepalive
```

Инварианты WARP-safe (зафиксированы, `CONFIG.generate` откажется собирать иначе):

- `S1..S4 = 0`, `H1..H4 = 1,2,3,4` — выводим всегда;
- `MTU` — по умолчанию `1280`, разрешён диапазон `1280..1420` (значения выше
  ломают связь с неизменённым сервером Cloudflare, поэтому 1280 — дефолт);
- `PersistentKeepalive` — по умолчанию `25`, только в секции `[Peer]`;
- `I1` — заглавное поле, цепочка только из `<b 0x..>`, `<r n>`, `<rc n>`, `<rd n>`;
- `AllowedIPs = 0.0.0.0/0, ::/0` — полный туннель, раздельного нет;
- `DNS =` — только IP (хостнейм резолвится сервером или, как запасной путь, DoH).

Пример того, что отдаёт страница (аккаунт и I1 каждый раз новые):

```ini
[Interface]
PrivateKey = WI/7+m6E1YKUdmE7ZTD2nOUm5d1Lp0OafS6Pg0Lvwlw=
Address = 172.16.0.2, 2606:4700:110:8be5:fa4f:a693:e855:8ff8
DNS = 195.133.25.16, 164.5.224.81
MTU = 1280
S1 = 0
S2 = 0
S3 = 0
S4 = 0
Jc = 4
Jmin = 40
Jmax = 70
H1 = 1
H2 = 2
H3 = 3
H4 = 4
I1 = <b 0xcf0000000101610000405712…><r 23><b 0x57d0a1622e193002…><r 16>

[Peer]
PublicKey = bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = 162.159.193.3:500
PersistentKeepalive = 25
```

### I1 (обфускация)

Четыре профиля — точный порт `config/i1.go`:

- `quic` (по умолчанию) — настоящий QUIC Initial: TLS 1.3 `HKDF-Expand-Label`,
  AES-128-GCM с AAD-заголовком, header protection (AES-ECB на блоке = AES-CBC с
  нулевым IV), varint'ы, маскирование первого байта и packet number;
- `dns` — DNS-запрос с EDNS0 padding, `sip` — SIP `OPTIONS`, `stun` — STUN binding;
- «своя цепочка» принимается после валидации, «без I1» — строка не выводится.

Тест `test.js` расшифровывает QUIC-пакет нативным `node:crypto` и сверяет
payload — «упростить» шифрование нельзя, это единственная гарантия, что
мимикрия остаётся настоящим QUIC.

### Junk-пакеты

Пресеты: `warpgen` (4/40/70 — как `config.NewConfig()`), `compatible` (4/64/96),
`balanced` (6/64/160), `enhanced` (10/96/320) и «случайно» (Jc 4..6,
Jmin 10..50, Jmax = Jmin + 20..100). Ручной ввод Jc/Jmin/Jmax в интерфейсе
пока не выведен (в ядре он поддержан).

### Endpoint

Случайный адрес из диапазонов WARP (`162.159.192.0/24`, `162.159.193.0/24`,
`188.114.96.0/22` — как в `scanner/`) × порт. Два набора портов: только WARP
(`500, 1701, 4500, 2408`) и широкий (как у публичных генераторов). Проверить
работоспособность из браузера нельзя — WARP слушает UDP, а `UDP` из `fetch`
недоступен; это подписано в интерфейсе, и никакого «сканера»-обманки нет.

## Ограничения и приватность

- Приватный ключ приходит с сервера в браузер — доверие к серверу обязательно
  (это и есть выбранная модель). Сервер ничего не хранит; ключ живёт только в
  памяти страницы и не пишется в `localStorage`.
- Аккаунт одноразовый: повторная выдача — новая регистрация. Cloudflare
  ограничивает частоту с одного IP (`error code: 1015`), поэтому сервер
  возвращает `RATE_LIMITED` и должен иметь свой лимит по IP.
- `peer_pub` у Cloudflare одинаков для всех, IPv4 (`172.16.0.2`) тоже, IPv6 —
  у каждого свой. Хранить `peer_pub` на сервере не обязательно: он приходит в
  ответе регистрации.
- Экспорт — только `.conf`. Ни Clash/JSON, ни QR, ни AWG 3.1, ни раздельного
  туннелирования.
- DNS проверяется «вообще», а не через туннель: сервер не строит туннель, чтобы
  проверить резолвер. Живость резолвера не гарантирует, что он ответит
  внутри WARP, но это единственная проверка без туннеля.

## Стиль и правки

- Вся логика — в `warpgen.js` (`window.Warpgen`); `app.js` только связывает
  разметку с библиотекой, `index.html` — разметка и стили, `dev-server.js` —
  только транспорт и регистрация.
- `CONFIG.generate(x)` — `async`; принимает либо входные данные (`{account,
  endpoint, dns, …}`), либо готовый конфиг из `CONFIG.build`. Второй вариант
  нужен, чтобы не собирать DNS дважды.
- Комментарии и интерфейс — по-русски. Внешних JS/CSS/шрифтовых запросов нет:
  шрифты лежат в `web/fonts/` (SIL OFL 1.1).
- Правка ядра требует зелёных `make web-test`; правка контракта — правка
  одновременно `API` (`warpgen.js`), `dev-server.js`, `test-server.js` и этого
  файла.
- Единственный класс скрытия — `.hidden` (`display: none !important`); `app.js`
  пользуется только им. Не «оптимизировать» в `[hidden]` или пустое правило:
  без `!important` его перебивают селекторы-идентификаторы вроде `#confBlock`.
- Палитра: фон `--bg #0B0B0B`, панель `#111111`, линии `#3A3A3A`, текст
  `#E9E6DE`, дим `#8B8A84`, сигнальный акцент `--accent #FF6A00`. Никаких
  градиентов, `box-shadow`, blur и скруглений — это проверяет `test-css.js`.
  Шрифты: Space Grotesk для заголовков, JetBrains Mono для данных.
- Фон — плоский `--bg` и слой `.bg` с тонкой сеткой (`z-index < 0`); фон
  **нельзя** задавать на `html`, иначе он перекроет слой. Для тёмных контролов
  достаточно `html { color-scheme: dark }`.
- Экрана два: главный (кнопка `#genBtn`, живая таблица параметров, порядок
  работы 01–03, футер) и выезжающая панель настроек **слева** (шестерёнка
  справа сверху, группы `01`…`06`). Результат — нижний sheet с логом статусов
  и конфигом; он открывается и при получении аккаунта, и при генерации. До
  первой генерации `#confBlock` скрыт классом `.hidden`.
- Статусы пишутся через `textContent`-эквивалент (экранируются): строки от
  API и ошибки не должны попадать в `innerHTML` как разметка.
