# Идеи и исследования: как получить не-RU локацию для внешних сервисов

Файл для заметок «на будущее». Ничего из этого пока не реализовано в коде.

## Почему перебор endpoint не помогает (измерено)

WARP выбирает выходной IP не по узлу `colo`, а по **исходному адресу, с которого его
видит Cloudflare**. Замер из РФ: `colo=HEL/FRA`, а `loc=RU` у 77 из 77 рабочих
endpoint'ов; `ipinfo.io` и `ifconfig.co` через туннель тоже видят Россию.

Отсюда общий принцип: бесплатный рычаг только один — **сделать так, чтобы Cloudflare
увидел подключение из другой страны**. Всё ниже — варианты, как этого добиться без
своего сервера.

---

## Вариант A. NAT64-«смена души» — НЕ реализуем сейчас, зафиксировано

**Суть.** Подключиться к WARP не напрямую по IPv4, а через **публичный NAT64-шлюз,
расположенный в другой стране**. Тогда Cloudflare видит подключение из Нидерландов/США
и назначает соответствующий выходной IP.

**Как собирается endpoint.** Адрес WARP-endpoint'а заворачивается в NAT64-префикс:

```
[NAT64-префикс]:[IPv4-в-hex]:[порт]
```

Пример (США): `[2602:fc59:b0:64::a29f:c702]:2408`, где `a29f:c702` — это `162.159.199.2`
в hex (`162→a2`, `159→9f`, `199→c7`, `2→02`).

**Публичные NAT64-префиксы** (из `BPB-Worker-Panel/docs/NAT64Prefixes.md`):

| Префикс | Локация |
|---|---|
| `2a02:898:146:64::` | Нидерланды |
| `2602:fc59:b0:64::` | США |
| `2602:fc59:11:64::` | США |

Расширенный список провайдеров: `nat64.net/public-providers` (Германия, Финляндия, UK).

**Требования и ограничения.**
- Нужен **IPv6** у провайдера/устройства (наш текущий стенд IPv6 не имеет — проверить
  не смогли).
- Шлюзы волонтёрские: бывают перегружены; `nat64.net` уже блокировал WARP-пользователей.
- Добавляется лишний хоп → выше задержка.
- Плюс: шифрование WARP сохраняется end-to-end, шлюз видит только шифрованный UDP к
  Cloudflare (в отличие от публичных SOCKS-прокси).

**Источники:** usque, «Soul Transfer: How to Forcibly Change Cloudflare WARP's Network
Location with NAT64» (discussion #74, март 2026); `BPB-Worker-Panel/docs/NAT64Prefixes.md`;
`nat64.net/public-providers`.

**Статус:** реализовывать не будем сейчас. Если понадобится — это правка только на уровне
выбора endpoint для туннеля (форма адреса), логика проекта не меняется.

## Вариант B. warp-in-warp — ПРОВЕРЕНО, не даёт не-RU

**Гипотеза из переписки:** цепочка из двух WARP, где внешний хоп приземляется в
нероссийский colo, а внутренний получает адрес по внешнему узлу («внутренний получает
адрес по внешнему узлу»). Ожидалось, что внешний узел Хельсинки/Варшава даст не-RU выход.

**Как проверяли.** Готовую реализацию взяли в warpscout (`-through ADDR` + отдельный
`outer`-аккаунт; скан идёт изнутри внешнего туннеля, каждый найденный endpoint — это
внутренний туннель). Аккаунт — `test-account.json` (в нём есть секция `outer`).

```bash
# рабочий внешний endpoint сначала ищем сканом (чистый WG не проходит, см. ниже)
warpscout scan -a test-account.json -p awg -gen-i1 quic -n 2 -no-report -t 2 -best

# сам тест: скан изнутри туннеля
warpscout scan -a test-account.json -p awg -gen-i1 quic \
  -through 8.39.204.217:1701 -inner-proto awg -n 2 -no-report -t 2
```

**Результат (2026-10-11), два прогона с разными внешними узлами:**

| Внешний endpoint | NODE всех внутренних | SEEN AS |
|---|---|---|
| `8.39.204.217:1701` | HEL (Helsinki, FI) — у всех | **RU** |
| `188.114.99.123:2408` | WAW (Warsaw, PL) — у всех | **RU** |

Задержка выросла до 400–710 мс (двойной хоп) против 76–200 мс напрямую.

**Вывод.** warp-in-warp **меняет узел (NODE)** — все внутренние туннели приземляются на
том же colo, что и внешний. Но **SEEN AS остаётся RU**: внутренний туннель выходит через
egress внешнего WARP, а Cloudflare и этот адрес геолокализует как российский. Регион —
неподвижная точка, вложение WARP её не меняет. Гипотеза из переписки не подтвердилась.

**Побочная находка (важная).** warpscout со штатным `-proto wg` (чистый WireGuard, без
обфускации) не нашёл ни одного рабочего endpoint из этой сети — 0/28. С `-p awg`
(AmneziaWG: junk + I1, мимикрия под QUIC) — 28/28. То есть **чистый WG-хендшейк тут
режется DPI, а обфусцированный проходит**; это подтверждает выбранную схему с
`Jc/Jmin/Jmax` + `I1`.

**Повторная проверка (2026-10-13), уже с живым внешним AWG-туннелем.** Раньше вывод
опирался на `-through`, где внешний хоп поднимался тем же инструментом; теперь внешний
контур — наш `.conf` в AmneziaVPN (`amn0`, `warp=on`, `colo=HEL`), а внутрь помещён
warp-plus. Итог тот же и уже без оговорок: вложенный WARP **поднимается и носит данные**
(контроль — 3.45 МБ/с; `warpgen dns-check` изнутри вложенного туннеля отвечает
`1.1.1.1` за 71–134 мс), но его внешний адрес — `2a09:bac5:…` (Москва, RU). То есть
регион **действительно неподвижная точка**: вложение WARP меняет узел, но не страну.

## Вариант C. WARP → Psiphon поверх внешнего AWG-туннеля — ПРОВЕРЕНО, даёт не-RU

**Суть.** Снаружи — наш AWG-конфиг из warpgen (в AmneziaVPN он обходит DPI, который режет
чистый WG), внутри — warp-plus в режиме `--cfon`: он поднимает свой WARP, поверх него
запускает Psiphon и отдаёт SOCKS5 на `127.0.0.1:8086`. Страну меняет именно Psiphon —
сам WARP из РФ по-прежнему выходит в Москве (`loc=RU`). Это первый проверенный вариант,
который реально даёт не-RU выход без своего сервера.

**Замер (2026-10-13, внешний туннель `162.159.192.175:4500`, `colo=HEL`, `warp=on`):**

| Запрос | Результат | ip | ASN | Время | Скорость |
|---|---|---|---|---|---|
| контроль (WARP без Psiphon) | работает | `2a09:bac5:5151:2db9::48e:54` (Москва, RU) | AS13335 CLOUDFLARENET | 6 с | 3.45 МБ/с |
| **NL** | работает | `172.233.49.7` | AS63949 Akamai (Амстердам) | 16 с | 0.64 МБ/с |
| **DE** | работает | `217.160.50.254` | AS8560 IONOS SE | 10 с | 0.59 МБ/с |
| **SE** | работает | `172.234.102.183` | AS63949 Akamai (Стокгольм) | 7 с | 0.77 МБ/с |
| **US** | работает | `107.170.5.190` | AS14061 DigitalOcean (Нью-Йорк) | 10 с | 0.31 МБ/с |
| **PL** | работает, страна спорная | `57.128.192.119` | AS16276 OVH | 10 с | 0.62 МБ/с |
| **FI** | НЕ работает (2 из 2) | — | — | ошибка через 60 с | — |

У PL один и тот же адрес видится как PL у `ipinfo.io` и как FR у `ifconfig.co` — по одному
геосервису судить нельзя. FI падает с `Unable to start psiphon: clientlib: tunnel
establishment timeout` при уже готовом WARP, то есть отказывает именно Psiphon-этап.

**Грабля warp-plus v1.2.6 (важно для повторения).** Проверка связи внутри утилиты —
HTTP-**HEAD** к `--test-url` с требованием кода ровно **200**. Cloudflare сейчас отдаёт на
HEAD `/cdn-cgi/trace` **404** (GET — 200), поэтому без обхода гейт не проходится ни на одном
endpoint: процесс умирает через 21–42 с с `context deadline exceeded`, а SOCKS-прокси даже
не поднимается. Обход — своя ссылка с HEAD=200: `--test-url http://example.com/`.

**Порядок повторения** (ключи не печатать):

1. `warpgen scan` → endpoint с NODE не DME/LED/KJA, затем `warpgen gen -endpoint … -output file.conf`.
2. Импортировать `.conf` в AmneziaVPN, подключить, проверить `curl -s https://www.cloudflare.com/cdn-cgi/trace` → `warp=on`, `colo` не DME/LED/KJA.
3. `warp-plus -4 -e 162.159.192.1:2408 --cfon --country NL --test-url http://example.com/`, затем `curl --proxy socks5h://127.0.0.1:8086 https://ifconfig.co/json` и то же к `ipinfo.io/json`.

**Наблюдения по реализации.** AmneziaVPN назначает адреса интерфейсу сам (`122.87.0.0/32`,
`fd58:baa6:dead::1/64`) — `Address` из нашего `.conf` на интерфейсе не появляется, на работу
это не влияет. Внутренний MTU warp-plus (1330) больше внешнего (1280), и данные всё равно
ходят: ядро фрагментирует внутренние пакеты, так что вложенность по MTU не ломается —
проверено и на скорости 3.45 МБ/с, и на DNS через вложенный туннель.

Подробности и сырые замеры: `psiphon-test-report-2.md` (таблица 12 прогонов),
логи — `/tmp/psiphon-test/logs/`.
